# Human2AI 项目交付与发布

这是源码仓库维护者使用的项目 Skill。消费项目使用的产品 Skill 位于 `skills/human2ai/`，两者职责独立。

## 确定本次范围

根据用户本次请求和会话中已有授权选择步骤，不因加载 Skill 就扩大操作范围：

| 用户意图 | 执行范围 |
| --- | --- |
| 提交、推送或创建 PR | 完成用户指定的交付步骤；不自动合并 |
| 合并指定 PR | 审查检查结果并合并；不自动发布 npm |
| 准备某个版本 | 更新版本、整理变更与验证证据、创建发布准备 PR |
| 发布某个版本 | 按已授权的发布目标完成安装包验证、npm 发布与 GitHub Release |

明确覆盖多个步骤的授权持续有效，无需逐步重复确认。目标包、版本或发布范围无法从上下文确定时，先完成可独立推进的检查和准备，再询问缺失信息。需要发布授权时，先提供版本、提交、目标渠道、待发布安装包与验证结果，使用户能审阅具体结果。

## 读取仓库事实

1. 从 Git 仓库根目录工作，遵循 `AGENTS.md` 中的分支、提交、数据目录与领域/UI 规则。
2. 检查 `git status --short --branch`、差异、远端与当前分支的 PR 状态。保留无关改动；已合并分支不继续开发，分叉历史先查明原因，不默认强推。
3. 从 `package.json`、锁文件和 `.github/workflows/` 读取包名、版本、验证命令及实际自动化行为。当前工作流做验证，npm 手动发布；若后续新增自动发布，先识别触发条件，避免重复发布。
4. 用 `git remote get-url skill-apps` 确认目标 GitHub 仓库。按实际远端选择 `gh --repo`；不把 npm 账号或 fork 的发布目标写死。

## 提交与创建 PR

- 新工作从最新的远端 `main` 创建功能分支；已有未合并功能分支可继续使用。工作区有无关改动时保留它们，必要时使用独立 worktree。
- 审查本次差异，运行与改动相关的验证。只暂存本次文件或对应片段，用中文提交信息，并检查暂存内容。
- 按用户授权推送：`git push skill-apps HEAD:refs/heads/<branch-name>`。不得直接推送 `main`，不得使用无目标的 `git push`。
- PR 目标为 `main`。描述最终改动及验证结果，多行正文使用文件配合 `gh pr create --body-file`；临时正文保存到忽略的 `.human2ai-data/output/`。
- 返回提交、分支、PR 链接和检查状态；只要求提交或建 PR 时到此完成。

## 合并 PR

- 确认目标仓库、PR、目标分支和最新 head 提交，审查最终差异与未解决意见。
- 检查最新提交上的三个现有工作流：`Release readiness`、`I18n semantic gate`、`Domain baseline gate`；以实际工作流和 GitHub 合并规则为准。
- 检查失败时先修复或报告具体阻碍，不绕过检查合并。已获合并授权且要求满足时执行合并；执行前再次检查工作区状态。
- 不自动删除远端分支；删除须符合 `AGENTS.md` 的明确分支确认要求。
- 返回合并提交与 main 检查状态；主分支检查失败不能作为可发布版本继续。

## 准备或发布版本

涉及版本准备、npm、GitHub Release 或发布中断恢复时，读取 [references/release.md](references/release.md)。仅提交普通改动或合并普通 PR 时无需加载。

## 保持文档职责

- 发布者的命令、账号准备和操作流程维护在本 Skill 中。
- README 面向访问者，介绍产品、安装和使用；只在版本影响公开安装说明时更新对应内容。
- AGENTS 保留日常开发约束，不复制本 Skill 的发版步骤。
- 产物、发布说明草稿和验证记录留在忽略的 `.human2ai-data/output/`；凭据不进入源码或输出。
